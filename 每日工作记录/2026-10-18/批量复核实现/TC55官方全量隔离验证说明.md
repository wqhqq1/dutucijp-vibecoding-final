## 失败、修复与复验

首次生成阶段 CPU 累计超过 122 秒，尚未保存推荐快照，专用进程被停止，副本保留。随后发现并修复销售关联查询的 SQL 计划：先取取消键，使用 CROSS JOIN 和销售身份索引，避免反复扫描百万行。第二个旧构建仍处于生成时被停止；两次中止没有作为通过证据。修复后实测生成约 2.17 秒。

12:37 首次完整功能运行的业务、审计、幂等及 300 次 HTTP 检查通过，但源主文件 SHA 从 `382df0b6830c8e638c35bafc3a83138e9a545e96f982f7094d3f3743509bf71e` 变为 `e4d05e159b285aac703421c18ac1d651eb379e2e3a6e2fcfdafc0add8876cfb7`，该轮结果为失败。验证器沿用了旧 `transactionverify` 的普通路径 DSN；modernc 驱动会忽略普通路径里的 `mode=ro`。虽然 `query_only` 禁止 SQL 写入，连接仍以读写模式打开，关闭可执行 WAL checkpoint，不能声称物理源文件未改。

验证器改用 `file:` URI，并在备份前强制检查驱动文件只读标志。新增两条回归：临时 WAL 数据库以带空格和 `#` 的路径打开时，驱动只读、SQL 写入被拒绝、读及关闭前后主文件和 WAL 散列不变；缺失源文件不得被创建。最后将相同语义集中为 `store.OpenReadOnlySource`，验证器包装调用该公共诊断辅助函数；无业务算法变化，未重复重型测量。集中后 `go test ./cmd/reviewverify -count=1` 再次通过，1.528 秒。

另用 Python `Path.as_uri() + '?mode=ro'` 的两个一致只读快照，对首次未产生复核写入的备份与 SHA 变化后的源逐行比较十张原业务表的完整内容散列。datasets、source_rows、normalized_rows、runs、decisions、sale_balances、allocations、candidate_evidence、cases、audit_events 全部相同，耗时 22.25 秒。没有读取认证表或真实凭据。该证据说明业务逻辑数据保持原样，不能把此前物理 SHA 失败改成通过。

采用真正文件只读连接后，在全新副本完整复验得到上述最终通过结果。最新生产守卫调整后的 TC49—54 及对应 HTTP 专项也复跑通过：store 1.789 秒、web 2.389 秒。
